# FEDS — плагин дизайн-системы FEroom для Figma

Плагин **дописывает** компоненты и блоки в уже работающую дизайн-систему FEroom: токены L3 (и при нехватке — L2), стили, документацию, спецификацию и мастер-компонент. Полное ТЗ: [docs/TZ.md](docs/TZ.md).

## Главное правило

Существующая трёхуровневая система токенов — **закон**. Любой новый компонент повторяет её грамматику, а не изобретает свою. Эталон разбора: [analysis/token-architecture.md](analysis/token-architecture.md), соглашения файла Figma (scopes, стили, иконки, публикация): [analysis/figma-conventions.md](analysis/figma-conventions.md).

Файлы Figma: источник токенов, стилей и иконок — «F · DS · Элементы · Основа стилей» (`niGA0qBFtb0PXKEIJIBrLe`); компоненты — «F · DS · Компоненты · Базовые» (`gaygUVaeJabe7eDT5rYYm4`), устройство разобрано в [analysis/components-structure.md](analysis/components-structure.md). Любые обращения к Figma на этапе анализа — только чтение. Машинный индекс: `analysis/token-index.json` (пересобирается `python tools/analyze_tokens.py`).

- `1. Primitives` (1 режим) — сырые значения. **Никогда не меняется.**
- `2. General` (light/dark) — семантика + размеры компонентов (`size/{component}/*`, `space/…`, `gap/…`, `radius/…`, `border/…`, `typography/{component}/…`, `effects/…`). Всё — алиасы на L1.
- `3. Components` (1 режим) — токены компонента, каждый — алиас на L2. Тема приходит через L2.
- Ссылки только вниз и только на соседний уровень: L3 → L2 → L1. Ссылка L3 → L1 — только явное исключение, помеченное в контракте.
- Имена kebab-case, разделитель `/`. Инверсия — сегменты `inverse-*`, а не отдельные режимы.
- Существующее не переименовываем и не «чиним» (даже опечатки вроде `box-uncheked`) без явного запроса.

## Решения автора (действуют, пока не отменены)

- **codeSyntax не заполняем** ни у новых, ни у существующих переменных (2026-09-21).
- **Эффект-стили не проработаны.** Их ошибки не исправляем, новые эффект-стили без запроса не создаём (2026-09-21).
- **`2. General / number`** не трогаем (2026-09-21).
- **Текстовые стили для компонентов не создаём**: у новых компонентов типографика привязывается к переменным `typography/{c}/…` напрямую. Блок TextStyle в плагине убран (2026-09-21).
- **Актуальные файлы ДС (`niGA0qBFtb0PXKEIJIBrLe`, `gaygUVaeJabe7eDT5rYYm4`) — только чтение.** Запись и проверка сборки — только в тестовом файле `wSWcfUravCxcymezdlNoko` (Elements), страницы `FEDS test / …` (2026-09-21).
- **Контраст WCAG AA обязателен** (текст 4.5:1, иконки 3:1, light и dark): на тёмной поверхности — только светлые `inverse-*`, иконка того же цвета, что текст, во всех состояниях. Проверка — `plugin/tests/a11y.test.ts`, отчёт по существующей палитре — `reports/a11y-contrast.md` (2026-09-21).
- **Одобренные исправления существующих токенов** (контраст): `button/text-button/inverse/text/*`, сообщения проверки и Label в `field/*`, плейсхолдер и маркеры `field/select/*` — помечены `change` в пресетах (2026-09-21).
- **Тёмная тема исправлена по WCAG AA** (колонка dark в `2. General`, 81 значение, `tools/dark_theme_fix.py`): насыщенные заливки темнеют под белый текст, calm/visited/soft — светлые сплошные ступени, рамки контролов ≥ 3:1. Новый L2 `on-bold` — белый поверх заливки (вместо `inverse-hard`, который в dark чёрный). Аудит — `tools/audit_contrast.py` → `reports/contrast-audit.md` (2026-09-21).
- **Модель новых компонентов** (`docs/build-rules.md` 2b): токены FEroom (можно дополнять и улучшать без разрыва зависимостей) → композиция по Atlassian Design System (признаки, не названия) → документация → правила сборки. Матрица ADS ↔ FEroom — `reports/atlassian-matrix.md` (2026-09-21).
- **Alert = Flag + Section message**: Appearance Subtle / Default / Bold, Bold сворачивается и не закрывается. Toast пока не закладываем. Hint = Spotlight (2026-09-21).
- **Светлая тема тоже исправлена до порогов AA** (`tools/light_theme_fix.py`, колонка light): насыщенные заливки на ступень плотнее, firm/calm/visited — сплошные ступени по состоянию, soft-текст и рамки контролов читаются (2026-09-21).
- **Toast пока не закладываем** (2026-09-21). **EmptyState** — документ в `input/backlog`, не трогаем.
- **Кнопки в других компонентах — кнопки системы; на тёмном — тип Inverse** (2026-09-21): у Button свои типы и четыре состояния, плюс общий тип Inverse у Filled (светлая заливка, тёмный текст), Outline (светлые рамка и текст) и Text (светлый текст), у Icon Only — Inverse-primary/secondary. Компоненты не заводят своих кнопок и токенов кнопок (приватная `_ Alert / Action` удалена); выбор типа — по WCAG на подложке хозяина (на жёлтом — обычные тёмные). Подложка одна в обеих темах (Alert Bold) — хозяин закрепляет светлую тему (`theme: light`). Типы под один компонент (On-bold, On-bright) не добавляются.
- **Семейства форм** (`docs/forms-architecture.md`): публикуется `Select` (Field: None/Vertical/Horizontal × Type × Size × Open × Inverse), части `_ Select / Button|Dropdown|Dropdown Items` приватные; Field не публикуется; Dropdown — механика (пресет `field-dropdown` вида `part`). Input — по той же схеме после согласования (2026-09-21).
- **Поля ввода и выбора собираются в Field** (как Input): Select → `Field / Select` (2026-09-21).
- **Загрузка = Skeleton** во всех текущих и будущих компонентах; ось Loading (спиннер) — только у контролов, которые ждут своего действия (Button). Неинтерактивные контейнеры (Alert и др.) без своих состояний и загрузки — `docs/build-rules.md` 2.5–2.9 (2026-09-21).
- Файл компонентов отстаёт от библиотеки (старые имена, удалённые переменные) — см. `reports/components-file-audit.md`. Эталон имён — **библиотека**, а не привязки в файле компонентов.

## Следующий этап: сборка остальных компонентов

Для **каждого нового** компонента `feds-spec-writer` готовит спецификацию (`specs-out/{c}.md` + `.spec.json`) по образцу секций «Спецификация» готовых компонентов, а `feds-component-builder` — архитектуру сборки (`presets/{c}.build.json`: наборы, оси, пропсы, слои, привязки к токенам пресета, проверка переключения пропсов) по `analysis/components-structure.md`. Описание сборки нового компонента — функция в `tools/gen_build.py` по образцу `alert()`; готовые компоненты — по образцу `button()` (повтор разбора из Figma).

## Порядок работы (фазы)

1. **Анализ** — изучить `input/` и токены, зафиксировать паттерны в `analysis/`.
2. **Описание всех новых компонентов** — пресет (`presets/`), токены (дифф), контракт (`contracts/`), спецификация (`specs-out/`) для **каждого** компонента из `input/backlog/`.
3. **Только после завершения фазы 2 по всем компонентам** — проектирование сборки компонентов и код плагина (`plugin/`).
4. QA и тесты на каждом шаге; приёмка по критериям раздела 7 ТЗ.
